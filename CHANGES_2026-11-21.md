# Driver and platform changes, 2026-11-21

These changes target the base PS4. Pro mode is not part of this work.

## Fixed

- **Thread suspension:** the suspend signal no longer collides with the kernel's `SIGBUS`, and a thread paused while leaving a system call reports its real stack.
- **CPU exception codes:** divide-by-zero and integer overflow are reported correctly.
- **Geometry shaders:** GS output now draws. The base PS4 uses a fixed 4 MiB GS ring window, so read descriptors cover the whole ring.
- **GS ring growth:** growing a ring no longer causes `VK_ERROR_DEVICE_LOST`.
- **Sockets:** sockets are really non-blocking through `SO_NBIO`, and message, IP, TCP and rlimit constants use the kernel's values.
- **File descriptors:** idle files are parked, so programs can keep more files open than the per-app limit.
- **Vulkan memory reporting:** one GPU pool was counted twice, so 1024 MiB was reported as 1919 MiB. Heap sizes, budgets and usage are now correct.
- **Shader cache:** the cache key includes the GPU address window that compiled shaders depend on.

## Faster or lighter

- **Windows-to-Unix crossing:** a 64-bit thread with a valid `FS` no longer makes a kernel call on every crossing. A near-empty Vulkan call went from 1175 ns to 63 ns, and a game-like draw from 6998 ns to 1909 ns.
- **Memory routines:** `libvulkan` uses SSE2 `memcmp`, `memcpy`, `memmove` and `memset`.
- **Garlic without a second copy:** a VRAM buffer now changes its own pages to Garlic instead of keeping a reserved Onion page under each Garlic page. With about 1 GiB of GPU buffers, the largest free direct-memory block stayed at 2383 MiB instead of falling to 1287 MiB. `ORBIS_GARLIC_MODE=copy` restores the old path.
- **Diagnostics:** per-draw counters run only with `ORBIS_COUNT_API=1`.

## Measured and rejected

- Moving RADV's per-draw upload buffer to Garlic showed no gain in the CPU-side benchmarks.
- `-march=btver2` without AVX made the game-like benchmarks slower.
- DXVK's default descriptor heap was faster than legacy descriptor sets.

## Test status

On the tested build, these suites pass: `archtest` 19, `fsprobe` 1, `systest` 44, `gsring` 10, `heaptest` 8, `drawbench` 8, `d3dbench` 8, `memplace` 6, `memstress` 48 and `pooltest` 3.

Minecraft and Horizon start on this build. Minecraft was checked to its menu with a 1536 MiB GPU pool, not in a world.

## Known problems

- **Muck crashes during startup.** The crash also happens with the old crossing and the old Garlic path, and its cause is not identified.
- **A pool that is too large can starve the game's CPU memory.** Minecraft failed during startup with a 2048 MiB pool beside its 1280 MiB Java heap.
- **Filling the GPU pool completely** can make the next submit return `VK_ERROR_DEVICE_LOST`, because RADV needs room for its own command memory.
- Minecraft can switch its saved renderer to OpenGL after a crash. Check `Using graphics backend` in its log when comparing runs.
